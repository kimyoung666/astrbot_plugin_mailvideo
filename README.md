# astrbot_plugin_mailvideo · 邮箱取址视频搜索

一个 AstrBot 插件：**登录邮箱（默认 QQ 邮箱）→ 发信 → 从回信正文提取站点地址 → 在该站按关键词搜索视频 → 把视频文件回传给用户**。

> 适用于「站点域名经常更换、通过邮件自动回复最新地址」这类场景：域名不写死在插件里，而是每次从邮箱回信中动态获取，站点换域名无需改代码。

---

## 功能流程

```
用户: /搜片 关键词
  │
  ├─ ① SMTP 向配置的收件邮箱发送一封邮件（主题/正文可配，正文即“任意消息”）
  ├─ ② IMAP 轮询收件箱，匹配到回信后，从正文中提取站点地址（自动过滤邮箱服务商/退订等噪声）
  ├─ ③ 用该地址作为站点入口，按关键词搜索视频（yt-dlp 通用解析，兼容 mp4 直链 / m3u8 / 播放页）
  ├─ ④ 列出候选清单，等待用户回复序号
  └─ ⑤ 只下载并回传用户选中的那一个视频
```

### 候选清单模式

搜索完成后**不会**自动下载，而是先把候选编号发给用户——用户明确选了哪一条，才去下载那一条，避免下错片子白等：

```
用户: /搜片 关键词
机器人: 📋 「关键词」共找到 12 个候选，回复序号选择：

        1. xxxxx
        2. xxxxx
        3. xxxxx
        ...

        回复数字即可（如「3」）· 回复「取消」放弃 · 180 秒内有效

用户: 3
机器人: · 已选择第 3 个：xxxxx
        ④ 开始下载…
        （随后回传该视频）
```

- 序号写法：`3`、`选3`、`#3`、`第3个`、`3号` 都认；
- `/搜片 3` 也可以（等价于回复 `3`）；
- 回复「取消 / 算了 / 放弃」放弃本次选择；
- 超过 `select_timeout` 秒未选择，清单自动失效；
- 群聊中只有**发起搜索的那个人**回复序号才有效，其他人回数字不生效；
- 选中的那条下载失败时，清单会保留，可以换个序号重试；
- 一次选一条；想再要别的，可以再回复清单里的另一个序号（清单未失效、未取消的前提下）。

## 指令

| 指令 | 别名 | 说明 |
|---|---|---|
| `/搜片 <关键词>` | — | 主流程：发信 → 取地址 → 搜索 → **列出候选**；回复序号后下载并回传 |
| `/搜片 地址` | `/搜片 取地址` | 只跑邮箱环节，返回并缓存当前站点地址 |
| `/搜片 邮箱` | `/搜片 邮箱测试` | 测试 IMAP/SMTP 连通性与授权码是否正确 |
| `/搜片 取消` | `/搜片 放弃` | 放弃当前待选的候选清单 |
| `/搜片 帮助` | `/搜片 help` | 显示用法与当前缓存地址 |

> 指令已统一为单一入口 `/搜片`：`<关键词>` 走主流程，`地址`/`邮箱`/`取消`/`帮助` 作为子指令关键词分发。
> 主流程结束后处于「等待选择」状态，此时**直接回复数字**（或 `/搜片 数字`）即可确认。

## 安装

1. 将 `astrbot_plugin_mailvideo` 整个目录放入 AstrBot 的 `data/plugins/` 下；
2. 在 AstrBot WebUI 的「插件」页重载插件，或在插件页点击刷新；
3. 若提示缺少依赖，插件会自动按 `requirements.txt` 安装（`yt-dlp` / `httpx` / `beautifulsoup4`）。

> 依赖 `ffmpeg`（用于 m3u8 合并、音视频合流）。请确保运行 AstrBot 的机器已安装并能在 PATH 中找到 `ffmpeg`，或在配置里填写 `ffmpeg_path`。

## 配置（WebUI → 插件 → 配置）

### 邮箱（必填）

| 配置项 | 说明 |
|---|---|
| `email_account` | 登录/发件邮箱地址，如 `123456@qq.com` |
| `email_auth_code` | **授权码**（不是登录密码），见下方获取方法 |
| `imap_server` / `imap_port` | 默认 `imap.qq.com` / `993` |
| `smtp_server` / `smtp_port` | 默认 `smtp.qq.com` / `465` |

### 收发信

| 配置项 | 默认 | 说明 |
|---|---|---|
| `recipient_email` | — | 收件邮箱（“用户设置的邮箱”）。插件向它发信并等待其回信 |
| `mail_subject` | `获取地址` | 发信主题。若对方是「关键词自动回复」服务，填其要求的触发词 |
| `mail_body` | `获取最新地址` | 发信正文 |
| `reply_wait_timeout` | `120` | 等待回信超时（秒） |
| `reply_poll_interval` | `5` | 轮询间隔（秒） |

### 固定站点

| 配置项 | 说明 |
|---|---|
| `site_1_enabled` / `site_1_address` | 第 1 个固定站点的开关与地址 |
| `site_2_enabled` / `site_2_address` | 第 2 个固定站点的开关与地址 |
| `site_3_enabled` / `site_3_address` | 第 3 个固定站点的开关与地址 |

三个站点按 1→2→3 顺序取第一个「已启用且非空」的地址；启用后直连该站点，完全跳过邮件取址。全部不启用时才走「发信→等回信」流程。

> **填发布页还是真实站？** 添狗（tiangou）系这类站，官网标称的「永久域名」（如 `www.tiangou2.cc`）只是**地址发布页**，页面上根本没有视频。启用站点适配器后，直接填永久发布页即可——插件会自动从发布页里解析出当前真实站点（真实域名经常换，写死会失效）。

### 站点适配器（SPA / JSON API 站）

| 配置项 | 默认 | 说明 |
|---|---|---|
| `enable_site_adapters` | `true` | 启用站点适配器。命中则短路通用解析，不适配的站点完全不受影响 |
| `melon_search_pages` | `3` | 吃瓜栏目搜索翻页数（每页 14 条，`0` = 不搜吃瓜） |
| `segment_host_fallbacks` | `ts2.zblsjy.com` | 分片 CDN 镜像域名，m3u8 里的分片域名失效时按顺序探测替换 |

有些站（如添狗 `tiangou` 系）用通用规则**永远抓不到**，因为：

1. 任何路径（`/index.htm`、`/type/10.htm`、`/search.htm`）都返回**同一份** JS 壳，内容是 `document.write(decodeURIComponent("..."))`，浏览器里看得见、`requests`/BeautifulSoup 里只有一段转义字符串；
2. 视频列表由前端 Vue 请求 JSON 接口渲染，服务器 HTML 里没有任何 `<a>` 指向视频；
3. 播放页也是壳，播放地址是前端用 `serial_number` 拼出来的 m3u8，页面里搜不到直链；
4. 标题还做了单字符替换表混淆（`decrypt-text`）。

适配器 `core/site_adapters.py` 针对这类结构走真实接口：

```
发布页 → (实体解码 + 探测 /data.json) → 真实站点
搜索   → GET {真实站}/search.json?search={关键词}&{csstime}
详情   → GET {真实站}/video/{id}.json        # 只有 serial_number，没有播放地址
播放   → {novel_domain}/m3u8/{serial_number}/index_domain.m3u8?{csstime}
标题   → decrypt-text 替换表还原 + HTML 实体反转义
```

**吃瓜（melon）栏目**额外接了一套：

```
搜索   → GET {真实站}/melons_0_{页码}.json    # 没有关键词接口，只能拉列表
         → 解密标题后本地过滤（最多 melon_search_pages 页）
详情   → GET {真实站}/melon/{id}.json         # melon.serial_number + melon_videos[].path
播放   → {novel_domain}/melon_m3u8/{serial}/{path}/index_domain.m3u8?{csstime}
```

吃瓜条目常有多段（`video_0`、`video_1`…），适配器会先探测哪些段真的能拉，按顺序返回，下载器取第一个成功的。

**分片域名自救：** 站点换 CDN 后，m3u8 里的分片域名可能已失效，而同一份分片在镜像域名下路径完全一致（实测 `ts2.ywqishu.com` 全线超时、`ts2.zblsjy.com` 正常 200）。适配器会抓 2KB 分片实测，确认镜像可用后把它登记进下载器的域名改写表，分片与密钥请求整批换域名；`segment_host_fallbacks` 可以自己补镜像。注意分片 CDN 是**直连优先**——走代理常常返回 200 但 0 字节。

`csstime` / `novel_domain` 从真实站 `/data.json` 读取，不写死，站点换 CDN 也能跟上。以后要加别的站，只需在 `core/site_adapters.py` 里新增一个带 `search()` / `media_urls()` 的适配器类，并注册进 `SiteAdapters.items`。

## QQ 邮箱：如何获取授权码

1. 登录 [QQ 邮箱网页版](https://mail.qq.com/) → 顶部「设置」→「账号」；
2. 找到 **POP3/IMAP/SMTP/Exchange/CardDAV/CalDAV 服务**；
3. 开启 **IMAP/SMTP 服务**（需要短信验证）；
4. 按提示生成 **授权码**（一串字母），填入插件配置的 `email_auth_code`。

> 其它邮箱同理：开启 IMAP/SMTP，使用其提供的授权码，并把 `imap_server` / `smtp_server` 改成对应服务商地址。

## 常见问题

**Q：提示授权码错误 / 登录失败？**
- 确认用的是「授权码」而非 QQ 密码；确认已在网页版开启 IMAP/SMTP；
- 可先用 `/搜片 邮箱` 测试连接。

**Q：一直等不到回信？**
- 确认 `recipient_email` 会回信（可先手动发一封测试）；
- 适当调大 `reply_wait_timeout`；确认 `mail_subject` 是对方要求的触发词。

**Q：搜不到视频 / 下载失败？**
- 该站可能不被 yt-dlp 支持，或搜索 URL 模板不对。请据该站实际搜索地址调整 `search_url_template`；
- 需要登录/风控的站，可填 `cookie`；
- 境外站点可尝试配置 `http_proxy`。

**Q：明明浏览器能打开、能看片，插件却一个候选都搜不到？**
- 典型是「SPA + JSON API」站（页面是 JS 壳，数据走接口，播放地址前端拼接）。自 v1.4.4 起内置站点适配器，`enable_site_adapters` 保持开启即可；
- 添狗（`tiangou`）系还要注意：`site_1_address` 填**永久发布页**（如 `www.tiangou2.cc`）就行，别填那种带端口的一次性真实域名——真实站会变，发布页不会；
- 日志里出现 `适配器：发布页 xxx → 真实站 yyy` 表示已自动反查到真实站；出现 `适配器请求失败 .../data.json` 属正常（发布页本来就没有这个文件）。

**Q：视频发不出来？**
- 多数平台视频消息有大小限制（QQ 通常 ≤100MB）。超过 `max_video_size_mb`（默认 1024MB）时会自动改为返回直链；
- `send_as=file` 可改走文件消息（部分平台不支持）。
- 发送成功后插件会立即删除本地视频与本次任务的缓存目录，不在磁盘留副本。

## 性能与调优（实测）

在 16 核、有代理的机器上，对同一个 321MB / 141 分片的 HLS 视频实测：

| 阶段 | 优化前 | 优化后 | 说明 |
|---|---|---|---|
| 搜索（含废模板） | 36.1s | 4.3s（热态 1.6s） | 模板内「yt-dlp 枚举 / HTML 解析」并发竞速，命中的模板会被记住 |
| 分片下载 | 13.7s（24MB/s） | 9.3s（36MB/s） | 分片流式落盘 + 1MB 读块 |
| 合并封装 | 11.2s | 7.3s | 磁盘 I/O 与封装开销，已接近下限 |
| **合计（不含发送）** | **27.0s** | **17.9s** | — |

几个实测结论，供调参参考：

- **连接池共享**：整个下载任务只建一个 Client——HLS 的 m3u8、加密密钥、全部分片共用同一个。连接池上限 = 线程数 × 2、keep-alive 30 秒；以前每个分片都新建一次 Client，等于每片重做一遍 TCP+TLS 握手（走代理时尤其贵）。
- **并发可以开大一点**：连接复用好之后单连接开销大幅下降，默认并发从 16/8 提到 **24/12**。实测里 32 线程掉速是旧版「每片一次握手」的量级，若你的源站仍会限速/排队，再降回 12-16 即可。
- **直连通常优于代理**：同一批分片，直连 16 连接 ≈ 18.9MB/s，代理 16 连接 ≈ 8.6MB/s。所以默认「媒体能直连就直连」是对的，被墙的域名会自动回退到代理。
- **搜索页的 yt-dlp 枚举是最容易踩的坑**：通用解析器碰到不认识的搜索页会一直等到 socket 超时，因此搜索阶段的超时被单独压到 10s 以内，并且与 HTML 解析并行，不再串行干等。

### v1.4.6 增补：从源头减少字节数

并发调到头之后，剩下的瓶颈通常不是「拉得快不快」，而是「拉多少」——尤其回传到平台是整包上行，上行带宽比下行窄一个量级。

- **`prefer_max_bitrate_mbps`（码率上限）**：master playlist 有多档清晰度时，原来一律取最高 BANDWIDTH。填 `2.5` 就取不超过 2.5Mbps 的最高一档，下载体积和上行字节同时砍半，手机屏幕上基本看不出差别。默认 `0` = 仍是最高画质。
- **预检复用播放列表**：体积预检拉过的 m3u8 会被缓存，下载阶段直接复用，少一次往返；预检的体积估算也改成按 BANDWIDTH 精算（原来是固定 1.5Mbps 估算，对高码率源会少算一半以上，导致白下几百 MB 才发现超限）。
- **`send_shrink_over_mb`（发送前瘦身）**：超过指定体积先压到该体积附近再发，上行时间按比例缩短。默认 `0`（关闭）——转码吃 CPU，2 核机器上 libx264 veryfast 约 2~3 倍速。**优先用 `prefer_max_bitrate_mbps` 从源头选低码率档，而不是靠这里压。**
- **阶段耗时日志**：下载完成会打一行「拉流 x.xs / 合并 x.xs / 均速 xxMB/s」，下次觉得慢可以直接定位是哪一段。

### v1.4.7 精简：删掉走不到的路径

站点适配器（tiangou 系）只会产出 m3u8，所以整套「直链 mp4 多连接 Range 下载」永远不会被走到，已连根删掉：

- 移除 `_download_direct` / `_download_ranges` / `_fetch_range` / `_probe_range_support` 四个方法，以及 `direct_parallel_workers` / `direct_parallel_min_mb` 两个配置项。mp4 直链仍由 yt-dlp 兜底，功能不丢，只是不再有多连接加速。
- 删掉零引用的 `probe_direct_url` / `_extract_media_url` / `list_output_files` / `build_search_url` / `_playable`，以及只写不读的 `_size_cache`、恒为 1 的 `max_results`。
- 合并私聊/全局两个消息钩子：补发待投递和候选选择处理现在都在 `on_any_message` 里，少一次重复触发。
- 修 `_mux_local_playlist` 的固定 120s 超时：改为按分片数放宽（最长 1800s），长片不会再被合并阶段判死。
